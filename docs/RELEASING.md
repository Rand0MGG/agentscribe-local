# 开发集成、安装包与更新

本文件是开发集成与发行的唯一操作入口。长期开发约束见 [AGENTS](../AGENTS.md)，模块契约见 [ARCHITECTURE](ARCHITECTURE.md)，使用说明见 [README](../README.md)。构建、签名与应用内更新是否已完成以“当前状态”和实际工作流为准，源码接入不代表安装态验收。

## 日常只需做三件事

1. **开工说明行为与接口。** 两端从同一已审核的 `main` 基线出发，可以并行修改共享模块；互不兼容的接口、数据格式或核心算法变更先约定契约。代理负责比较分支、识别重叠和说明影响，不要求用户逐个文件协调。
2. **小批次审查和集成。** 一项可独立验证的改动完成后，审查并经用户同意合入 `main`，另一端同步这份代码再继续。代码合并不等于发行。
3. **需要给用户更新时准备发行。** 选择版本、平台和渠道，自动生成安装包与草稿；验收后发布，自动推进相应更新订阅。日常推送不发行。

## 两端并行与冲突

继续使用 `windows`、`mac`、`main`，不另设计团队分支体系。两端可同时修改共享代码，开工检查共同基线和远程差异，小批次审查后及时集成；接口或数据格式变化先对齐契约。文本冲突逐处合并，语义冲突检查组合行为并回归，不用整文件覆盖或保留两套业务流程解决。具体规则只在 [AGENTS](../AGENTS.md#分支与合并) 维护。

## 发行自动化

### 选择版本

版本含义遵循 [AGENTS 的统一版本规则](../AGENTS.md#版本与各平台独立发布)，不是提交次数。尚未完成目标平台验收的预览轮次递增 `beta.N`；正式版之后的兼容性修复递增修订号，新功能递增次版本号。例如：`0.6.0-beta.1` → `0.6.0-beta.2` → `0.6.0-beta.3` → `0.6.0` → `0.6.1`。跳号本身并非格式错误，但不能靠改成 `0.6.1` 代替正式版验收。

准备版本时同步 `pyproject.toml`、`linguaflow/__init__.py` 和当前打包说明；构建脚本从应用版本生成产物名称和清单。历史 Release 说明、已发布标签与安装包保持原样，README 下载链接继续指向实际存在的安装包。普通开发提交不必逐次改版本，合入 `main` 也不会自动创建 Release。

准备与发布是两个动作，中间保留现有的用户验收，不增加额外提案或审批文件。

```text
平台分支开发 → 代码检查 → 用户审查 → main 固定提交
                                           ↓
                          准备发行：选择版本/平台/渠道
                                           ↓
                两端原生构建 → 签名与安装升级检查 → Release 草稿
                                           ↓
                          用户验收，发布同一批已检查的文件
                                           ↓
                         更新对应 appcast → 应用内收到更新
```

`.github/workflows/prepare-release.yml` 提供“准备发行”工作流，手动选择固定 `main` 完整提交 SHA、已存在的不可变版本标签与目标平台；版本和渠道从该提交读取，不能在构建中临时改源码。版本准备仍先在平台分支提交、审核并集成。一个版本对应一个来源提交，两端可以仅发布已验收的一端。构建、签署已封存字节、草稿上传分别受 `release-build` / `release-draft` 环境保护；正式发布后再显式触发订阅工作流。工作流随 0.8.0 源码集成上传，尚未运行远程发行任务。

工作流只调用仓库中的生产构建脚本；本地复现与 CI 不维护两份打包标准。平台锁文件、原生启动器、更新组件和构建脚本一起提交，变更构建方式后仍从新固定提交构建。选择支持目标架构的运行器，不能把 `macos-latest` 的名字当作 arm64 保证；需要系统窗口服务的探针在具备条件的环境执行。

每个产物记录版本、平台/架构、来源提交、构建与依赖摘要、最低系统要求、文件摘要及签名状态，排除本机路径和用户数据。构建失败不推进订阅；缺签名或平台验收时保留草稿，不把开发测试通过当成可发行。

自动检查除现有源码 CI 外，还需验证安装包在无开发环境的路径启动、原生依赖完整、旧安装版到候选版升级、数据/模型保留、失败恢复与重启。常规包检查不访问音频设备；涉及识别、设备或录音生命周期的改动，在授权的目标机器补做实机检查。干净构建机不能替代 GPU 和真实录音验收。

发布阶段使用已有验收的产物，不能重新构建一份未检查的包；核对不可变标签指向、版本与来源提交一致，上传安装包、SHA256 和构建清单。版本展示与更新器排序值由同一版本规则生成，测试 beta→beta、beta→稳定及稳定版不接收 beta，不能按字符串排序或用工作流运行号替代来源版本。

发布成功后由同一发行工作流显式调用订阅生成/部署步骤，或显式 dispatch；不能假定 `GITHUB_TOKEN` 创建 Release 后会自动触发另一条 `release` 工作流。用户通过 GitHub 页面直接发布的入口也必须接入同一发布逻辑。订阅失败保留旧入口并允许仅重试订阅发布，不能改写已发布包。[GitHub 的触发限制](https://docs.github.com/en/actions/concepts/security/github_token)

Pages 发布会替换整个静态站点，因此全仓订阅发布共用一个串行锁，不只按平台/渠道锁定。生成时保留整套既有订阅，只替换本次选中的有效条目；部署前再次比较版本，旧任务不得覆盖新记录或清空另一平台入口。验收需覆盖两端先后发布、重复发布、订阅部署失败重试以及未验收产物不进入订阅。

安装包放 GitHub Releases；订阅放 GitHub Pages，通过 Actions 部署，不为此建立开发分支或自建服务。只更新选中的平台/渠道，保留其他入口。签名私钥保存在受保护的发布凭据中，不提交源码；普通 PR/开发检查不取得发布密钥。GitHub 支持以 environment 限制发布任务与凭据，实际配置须另行实施。

## 应用内更新

采用 Mac Sparkle 2、Windows WinSparkle + Inno Setup。共享代码只管理录音、保存、环境兼容及能否退出；原生组件负责下载、签名验证、程序安装和重启，不重复维护一套 Python 自替换器。安装版的“检查更新”接入组件；源码版仍提示源码更新。

用户在应用内确认后完成下载和安装，无需浏览器、拖动 `.app` 或重新走安装向导。安装器有进度与失败反馈。后台检查/下载遵守联网偏好；更新请求不上传录音、字幕或课件，也不因检查失败阻断本地使用。

录音中可以按联网许可下载，但不得安装、终止录音或重启。录音结束、磁盘保存成功、相关自有进程释放后再执行已确认的更新；未保存或收尾失败则延后并解释原因。下载或验证失败保留当前版本。程序替换失败恢复与新版启动失败恢复分别实现和测试，不假定 Sparkle/WinSparkle 已提供业务级自动回滚。

应用资源只读；录音、模型、运行组件与偏好留在独立用户目录。识别运行环境包含稳定路径下的自有基础 Python，不依赖更新时被替换的程序包。运行环境按 Python ABI、依赖锁、平台与后端判断兼容，不以应用版本每变一次就重装。

兼容环境直接复用；需要新环境时自动在最终独立路径创建、安装并验证，再切换版本记录，不让用户手动修复。应用与所需环境的准备/切换须协调：新环境失败时旧版仍可运行；旧环境和旧版保持对应关系，不能只恢复程序却仍使用不兼容的新环境。沿用当前独立目录与 `active.json` 机制，补齐基础 Python、兼容元数据和失败恢复。模型只有版本或格式确实变化才另行准备。

## 打包标准变化以后

更新器接收的是带签名的发行产物，不关心构建脚本用了哪种编译器。更换构建工具、调整包内目录或锁定新依赖，只要旧客户端仍能验证和安装该产物，应用身份与用户数据兼容，就能继续自动更新。

以下是必须兼容的边界：稳定的 appcast 地址、更新公钥/签名信任、Mac bundle ID / Windows 安装身份、平台与最低系统要求、旧安装器能处理的产物格式、用户数据格式，以及应用与运行环境的版本关系。更新组件不保证识别环境回滚或新版本启动健康检查；这些必须由应用实现并用真实旧包到候选包验证，不能只检查候选包能单独启动。

不能兼容时先发**过渡版本**：使用旧更新器能安装的格式和签名，带上新更新器、迁移逻辑或新的订阅地址；旧入口先提供过渡包，过渡版再从新入口升级到目标版。保留旧入口和信任所需的材料，覆盖从已支持旧版连续升级的测试。签名信任已丢失或旧客户端根本无法运行时，过渡升级不一定可行；不能承诺任何打包变化都可以无感升级。不能先改订阅格式或丢弃旧私钥，再让用户自行重装。无法保证自动迁移的变化应先修兼容，而非直接推送。

构建标准不在聊天里维护：机器执行的标准由脚本、依赖锁和更新配置定义，本文说明执行顺序与兼容要求。规则变更与代码同批审查，自动化调用新脚本即可；修改产物格式或升级协议时必须同时更新过渡路径和旧版升级测试。

### 更新发布操作

1. `packaging/updates.json` 已固定对应平台的 Base64 公钥。生产私钥由 Sparkle 官方工具生成并存放于登录钥匙串账户 `io.github.rand0mgg.agentscribe.macos` / `.windows`，仍需从原钥匙串安全部署；三个发行环境已建立，仅允许 `main` 工作流并要求仓库所有者审批。部署 CI 时分别托管为 `release-build` 环境的 `MACOS_UPDATE_PRIVATE_KEY` / `WINDOWS_UPDATE_PRIVATE_KEY`，不得进源码、构建清单、日志或普通检查。`sign_update_artifact.py` 只接受与固定公钥匹配的 32-byte seed 或 64-byte seed+public 格式。
2. 审查并集成源码、选择新版本、固定不可变标签。Mac 运行 `scripts/build_macos.py --fetch` 后运行 `scripts/build_macos.py`，默认嵌入固定 Sparkle、更新身份、原生驱动与恢复组件。`--without-updater` 仅供开发/过渡包，不能进入订阅。Windows 在 x64 MSVC 开发命令行运行 `python scripts/build_windows.py --fetch`，再运行同一脚本生成载荷，随后运行 `python scripts/build_windows_installer.py --payload <载荷目录> --fetch`；使用完整便携 CPython、Node、锁定桌面依赖、Qt 实际 PE 依赖和许可，不能复制开发虚拟环境。两端共用受 Git 跟踪的 `.py` / `.mjs` 应用文件清单完成复制与来源摘要；新增资源格式须在共享复制入口声明，本地忽略/未跟踪文件不入包。启动探针从外部目录与干扰 PYTHONPATH 运行，要求只导入包内代码。完整无音频包探针还检查窗口、WebEngine 渲染、Node/npm、venv、依赖及更新/恢复组件加载；Windows 在加入更新组件后、封装前执行，Mac 在最终 DMG 只读挂载后执行，失败不封存产物。
3. 正式发行还需配置 Mac Developer ID / 公证与 Windows Authenticode；当前脚本未自动执行这两种系统签名，不能把更新 Ed25519 签名当作系统签名。对最终文件完成系统签名后同步构建清单摘要/字节数，再用 `scripts/sign_update_artifact.py --artifact <文件> --manifest <构建清单> --target <平台>` 签署，密钥只通过受保护环境传入；得到纯 Base64 `.dmg.ed25519` / `.exe.ed25519`。已封存文件不可再改变，修改后必须重新封存、签名和验收。
4. 将安装包、SHA256、同名 `.build.json` 和 `.ed25519` 放入 Release 草稿；`prepare-release.yml` 会拒绝覆盖已发布 Release 和同名附件。验收下载、取消、签名篡改拒绝、断网、录音中等待、保存失败、退出资源释放、安装失败保留旧版、重新启动、启动失败恢复及数据/模型/运行环境兼容。Mac 隔离探针不是正式签名候选包，也不能替代 Windows 原生验收；只发布通过验收的平台。
5. 配置 GitHub Pages 使用 Actions 部署，以及 `release-updates` 受保护环境。发布已验收的同一批 Release 文件后，手动触发 `publish-updates.yml`，填写固定 `tag`、`target`，仅在该平台真实升级已验收时勾选 `accepted`。首次空站点才使用 `initialize`；已有站点必须先导入整站快照，不能覆盖。工作流串行保留其他平台、其他渠道及站点文件；使用无缓存快照请求减少陈旧 CDN 快照覆盖风险。生产环境首次部署仍需核查 Pages 地址和订阅可达性。

稳定/测试版按版本后缀生成各自订阅，安装器保留稳定应用身份。Mac 自定义驱动将检查、进度和结果送回共享反馈弹窗；Windows 原生 API 的下载/安装界面由 WinSparkle 提供，仍有原生提示，不能声称已经完全采用共享样式。已发行 beta.2 没有更新器，需要一次手动安装过渡包，之后才可使用上述流程。当前开发不移动已有标签、不覆盖已发布附件，也不自动发布订阅。

### 新版启动失败恢复

安装前后台复制并逐文件校验完整旧程序，在稳定用户目录准备独立基础解释器和恢复观察器，完成握手后才允许原生更新器安装。入口在导入 Qt 前登记新版进程身份；主窗口成功显示后确认启动健康。健康范围是桌面引导成功，不包含 GPU 推理、真实录音或所有课程组件。故意在登记身份后、窗口创建前抛出异常已验证恢复旧包、重新启动并告知用户；录音、模型和偏好不参与程序替换。

观察器只退出登记且创建时间仍一致的自有进程，完整退出后原子交换目录，保留失败的新包。若解释器在登记前损坏、观察器无法确认进程归属或无法退出，保留旧备份并标记需要恢复，不自动覆盖可能正在使用的安装。最新健康旧备份保留到下一次更新已准备并校验新备份后清理；失败或人工恢复材料不自动删除。
