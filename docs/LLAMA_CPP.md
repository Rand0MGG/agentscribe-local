# llama.cpp 翻译引擎

## 使用

“设置 → 翻译模型”先选择推理引擎，再选择该引擎的模型和计算设备。

| 引擎 | 模型输入 | 设备 |
| --- | --- | --- |
| PyTorch | 原有 HY-MT2、NLLB、兼容 Hugging Face 模型目录 | CPU；Windows CUDA |
| llama.cpp | 内置 HY 1.8B Q4_K_M，或本地 GGUF 指令模型 | Mac CPU / Metal；Windows x64 CPU / CUDA / Vulkan |

两种模型选择分别保存。已有配置保持 PyTorch；此前直接选择 Metal 的配置迁移到 llama.cpp。Mac 的 HY 快捷按钮选择内置 GGUF 和 Metal，不改变原先的 PyTorch 模型选择。

“下载 / 检查翻译模型”准备所选平台的固定 b11254 运行组件。内置 HY 下载固定 revision 的官方 Q4_K_M；自定义模型需自行准备 GGUF 文件，此按钮只校验本地文件并准备运行组件。安装不加载模型或访问音频设备。

也可在项目根目录执行：

```bash
# Apple Silicon
.venv/bin/python scripts/install_llama.py --device metal

# Windows PowerShell：CPU、cuda、vulkan 三选一
.venv\Scripts\python.exe scripts\install_llama.py --device cuda
```

## 兼容范围

- GGUF 是文件格式。FP32、FP16、量化精度由具体权重决定；引擎选择不会转换或量化文件。
- 当前内置并实测的模型为 HY 1.8B Q4_K_M。自定义文件必须是当前 llama.cpp 支持的架构，并适合通过聊天模板完成翻译指令；文件头校验只检查准备状态，实际加载还可能报告架构或模板不兼容。
- 初译、上下文、队列、缓存和字幕状态复用共享流程。llama.cpp 的通用翻译提示词与 HY 相同，新模型的语言质量、指令遵循和是否输出额外说明需单独验收。
- 当前服务上下文为 4096 token，最多生成 1024 token。请求前用本地聊天模板和分词接口检查完整输入，预留输出空间；超限时先移除最远的背景并提示，绝不截断待译原文。完整原文自身仍超限则报告错误并保留已有文字。生成参数集中于 `translation_models.py`。
- 初译默认前 1 段、定稿默认前 10 段已定稿原文；已排队的相邻同阶段请求最多合并 4 段、1200 字符，共享一次背景。批量响应使用按字幕 ID 返回的 JSON schema，校验缺失、额外或重复 ID 和空译文；字幕时间与原文分段保持对应。详见 [上下文翻译](CONTEXT_TRANSLATION.md)。
- GPU 选择当前使用该后端的首个设备，要求全部层加载到 GPU；不提供多卡选择或部分卸载配置，不静默切换 CPU。
- Windows 使用同一版本 CPU 主程序与所选 GPU 组件，CUDA 额外准备对应运行库；依然需要兼容的显卡驱动。Windows ARM64 和其他系统尚未提供此安装入口。

## 进程与离线行为

翻译服务只绑定 127.0.0.1，每次启动生成独立认证信息，客户端忽略系统代理。会话停止、取消或父进程退出时释放自己启动的服务。Windows 管道使用 PeekNamedPipe 检测断开，POSIX 使用 select；平台处理集中在 `process_platform.py`。

服务显式使用 `--cache-ram 0 --no-cache-idle-slots`，关闭历次请求的主机内存提示词缓存。固定 b11254 的默认上限为 8192 MiB，会在连续翻译中逐渐保留旧请求的 KV 状态；对 8GB Mac 尤其容易造成交换空间增长。当前推理槽所需的 KV 缓冲、相邻请求的前缀复用、应用的 512 条译文缓存和前后文翻译仍保留。关闭历史缓存可能增加再次遇到旧提示词时的计算量，不能据此保证整机内存或所有会话速度。

准备后只读取本地模型。桌面预检会提示缺少的文件；实际模型加载或翻译失败会报告错误，不将空白或达到输出上限的译文标记为成功。

### 长课堂积压排查（2026-10-02）

- M2 / 8GB、macOS 26.6.2、Python 3.12.14：在现有约 49 分钟课堂会话继续收尾期间做只读检查，没有停止、重启会话，也没有访问音频设备或另开模型推理。llama-server 内存足迹约 5.8 GiB，其中大块 malloc 分配约 5.5 GiB、大部分被换出；MLX 子进程约 1.6 GiB，整机交换空间约 9.2 GiB。RSS 不能代表这些进程包含换出页的全部内存足迹。
- 实际运行组件的 `--help` 确认历史提示词缓存默认上限 8192 MiB，现有服务启动参数没有覆盖它。固定版本[参数定义](https://github.com/ggml-org/llama.cpp/blob/b11254/common/arg.cpp)与[服务实现](https://github.com/ggml-org/llama.cpp/blob/b11254/tools/server/server-context.cpp)确认该缓存保存旧提示词状态、用 `--cache-ram 0` 关闭。大块分配与这一缓存机制相符，但没有提取每个活动分配的来源，不能将全部增长证明为缓存，或宣布已排除其他泄漏。
- 另外复现字幕层全历史 `SequenceMatcher(autojunk=False)` 的计算增长。对相同的 36,451 字符课堂定稿前缀追加一个合成短尾部，隔离 cProfile 检查中，修改前约 21.59 秒 / 9388 万次调用，首轮只比对尾部的修复约 0.00022 秒 / 134 次调用。真正的历史纠正仍重新打开受影响行。这是字幕映射的局部计算测量，使用模拟边界和时间跨度，包含 profiler 开销，不是 ASR、SaT 或整场性能验收；下方记录随后加入稳定前文的当前规则和测量。
- 回归覆盖 CPU / Metal / CUDA / Vulkan 的启动参数，以及长定稿前缀后追加、修订、定稿时的字幕 ID 和完整文字保留。本次修改需要当前会话自然处理结束后重启应用才能生效；尚未用修改后的模型服务重新完成 50 分钟课堂或验证其实际内存曲线，Windows 仍待实机验证。

### 比对滑动窗口的稳定前文（2026-10-02）

- 按用户选择，字幕版本比对带入最近 10 条稳定字幕段，加上全部可修订文本。计数单位是 SaT 分句后已经定稿的字幕段，可能含多个标点句；前文数量不足时全部带入。这只改变文字版本比对，ASR 音频窗口、SaT 的分句范围和翻译前后文设置沿用原有规则。
- 每次先验证已定稿文字是否仍是当前识别结果的完整前缀。更早位置发生改写时，从首条受影响字幕重新打开，向前带入最多 10 条仍未变的字幕。例：100 条稳定字幕时通常带第 91–100 条；上游改写第 75 条时，比对从第 65 条开始，包含第 65–74 条稳定前文和第 75 条至末尾的修订范围。比对不会主动重跑 ASR，也不会自行发明历史纠正。
